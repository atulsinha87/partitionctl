# v0.0 spike results

Run 2026-08-07 against real servers in Docker. Every line below is measured, not read.

Servers: **PostgreSQL 17.10** (aarch64, Debian) and **PostgreSQL 14.23**, the floor named by `NFR-COMPAT-1`.

---

## Headline: the TRD is wrong about REINDEX

`REINDEX INDEX CONCURRENTLY` and `REINDEX TABLE CONCURRENTLY` **both work on partitioned relations**, on 14.23 and 17.10.

```
PG 17.10   REINDEX INDEX CONCURRENTLY orders_created_at_idx;   -> REINDEX (exit 0)
PG 17.10   REINDEX TABLE CONCURRENTLY public.orders;           -> REINDEX (exit 0)
PG 14.23   REINDEX INDEX CONCURRENTLY o_idx;                   -> REINDEX (exit 0)
PG 14.23   REINDEX TABLE CONCURRENTLY o;                       -> REINDEX (exit 0)
```

After reindexing a 12-partition table through the parent index:

| Check | Result |
|---|---|
| Leaf indexes valid | 12 of 12 |
| Leaf indexes still attached in `pg_inherits` | 12 of 12 |
| Parent index `indisvalid` | true |
| `_ccnew` / `_ccold` leftovers | 0 |

PostgreSQL loops the partitions itself, one per transaction, at `ShareUpdateExclusiveLock`. Reads and writes continue throughout.

### Where the error came from

An earlier `WebFetch` summary of the PG17 `REINDEX` page asserted "partitioned tables and indexes are NOT supported with `REINDEX CONCURRENTLY`." That was the summarising model's misreading; the doc text it quoted says only that each partition is reindexed in a separate transaction and that the command cannot run inside a transaction block. Neither excludes `CONCURRENTLY`.

That misreading was repeated in conversation, written into TRD §7.2.11 and `FR-REIDX-2`, and used to justify the shape of M3 and the `<partitionctlReindexGate>` design. **A secondary source was treated as settled fact when a fifteen-minute experiment was available.**

---

## Question 1 — attached-leaf reindex: YES

`REINDEX INDEX CONCURRENTLY` on an individual leaf index that is already attached to a partitioned parent succeeds, and the attachment survives the internal index swap. Confirmed on 17.10 as part of the run above.

So both paths work: reindex the parent and let PostgreSQL loop, or drive the leaves individually.

## Question 2 — lock levels: two TRD errors

Measured by holding each statement in a transaction and reading `pg_locks` for the same backend.

| Statement | Object | Lock actually taken | TRD §7.2.2 claims |
|---|---|---|---|
| `CREATE INDEX ON ONLY <parent>` | parent **table** | **`ShareLock`** | `ShareUpdateExclusive` ❌ |
| | the new index | `AccessExclusiveLock` | not mentioned |
| `ALTER INDEX ... ATTACH PARTITION` | child index | **`AccessExclusiveLock`** | `ShareUpdateExclusive` ❌ |
| | parent index | `ShareUpdateExclusiveLock` | — |
| | parent + leaf tables | `AccessShareLock` | — |
| `COMMENT ON INDEX` | the index | `ShareUpdateExclusiveLock` | n/a, new |

**What this means in practice.**

`ShareLock` on the parent table conflicts with `RowExclusiveLock`, so `CREATE INDEX ON ONLY` **blocks writes** to the partitioned table while it runs. It is catalog-only and a partitioned parent holds no data, so the window is milliseconds — but goal `G3` ("zero write-path downtime") is overstated as written, and §7.2.2 is simply wrong about the lock.

`ALTER INDEX ... ATTACH PARTITION` takes `AccessExclusiveLock` on the **child index**, not on any table. `AC-8` is scoped to user tables, so it still holds, but the §7.2.2 entry is incomplete.

Neither finding requires an M1 code change. Both require a TRD correction.

## Question 3 — comment as a provenance marker: viable

```
COMMENT ON INDEX ... IS 'partitionctl run=test digest=abc123';
  before reindex:  partitionctl run=test digest=abc123
  after  reindex:  partitionctl run=test digest=abc123
```

The comment **survives `REINDEX CONCURRENTLY`**, and setting it takes only `ShareUpdateExclusiveLock`. The proposed fix for the `INV-1` / `AC-6` contradiction is therefore workable: mark the object itself rather than keying a side table on a name.

## Consequences

**Unblocked.** M3 is no longer gated. `NFR-COMPAT-1` (14+) is confirmed for the reindex path on both ends of the range.

**M3 collapses in size.** PostgreSQL already does the per-partition concurrent loop. PartitionCTL's remaining value for reindex is pacing between partitions, resume that does not redo completed partitions, progress and ETA, and leftover cleanup after a failure. The simplest honest implementation is a **single** `index.reindex_concurrently` node targeting the parent, with a per-leaf graph only when pacing or fine-grained resume is asked for.

**The project's premise is untouched for create.** `CREATE INDEX CONCURRENTLY` genuinely is unsupported on a partitioned parent; that gap is real and is what M1 fills. Reindex was never as strong a case, and is now weaker still. Say so plainly rather than defending it.

## Document changes required

| Where | Change |
|---|---|
| TRD §7.2.11 | Rewrite. The "PostgreSQL will reindex a partitioned index for you and that is the trap" framing is inverted: `CONCURRENTLY` works and is safe. |
| TRD `FR-REIDX-2` | Currently forbids reindexing the parent directly. Reverse it: the parent-level command is the default path. |
| TRD §7.2.2 | Fix the lock column for `index.create_parent_invalid` (`ShareLock`) and `index.attach` (`AccessExclusive` on the child index). |
| TRD §4.1 `G3` | Qualify "zero write-path downtime": one brief `ShareLock` on the parent table during `CREATE INDEX ON ONLY`. |
| TRD §16.4 | Spike is complete. Replace with a pointer to this file. |
| HANDOFF §7 P4 | Void. It assumed a parent-level reindex always fails. |
| HANDOFF §7 P3 | Still valid, and now cheaper: the reindex gate asserts catalog health, which needs no state store. |

## Reproducing

```bash
make db-reset && make demo
docker exec -i partitionctl-pg psql -U postgres -d postgres \
  -c 'REINDEX INDEX CONCURRENTLY orders_created_at_idx;'
```

Lock measurement uses `BEGIN; <stmt>; SELECT ... FROM pg_locks WHERE pid = pg_backend_pid(); ROLLBACK;` which works for any statement that is transactional. `CREATE INDEX CONCURRENTLY` is not, and was not measured; its `ShareUpdateExclusiveLock` is well established.
